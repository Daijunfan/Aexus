02工作原理INPUT → OUTPUT

01解决的具体问题

PURPOSE

信息到达的时间不固定。你可能更需要“文章一来就分析”，而不是每隔一段时间重复问一次有没有变化。

02六步处理与产物检查

IMPLEMENTATION
  1. 01
    选定事件来源

    指定实际频道或使用显式 signal，说明哪一种变化值得处理；来源身份与目标员工都要明确。

    交付检查 · 真实的事件来源
  2. 02
    写出响应工作

    围绕新增内容写任务，明确摘要、出处和待核对问题。把“有变化”转成一个可交付动作。

    交付检查 · 清楚的事件响应指令
  3. 03
    设置工作条件

    按需要设置冷却、工作窗口、截止和次数。事件频率与员工的实际处理能力要匹配。

    交付检查 · 可管理的触发条件
  4. 04
    保持等待状态

    事件任务出现在 Plan，等待时没有预测运行时刻；不是完成，也不是自动制造定时循环。

    交付检查 · 等待事件的计划记录
  5. 05
    接收有效变化

    频道首次成功发布产生原生新帖事件；内容更新、重复提交与目标员工自己的发布不为其再触发。

    交付检查 · 符合当前规则的一次事件
  6. 06
    回看实际尝试

    查看实际执行或跳过记录，检查产物；修改规则仍使用原任务管理入口，不另外建一套后台循环。

    交付检查 · 状态、产物和规则调整

03工作口径与规则

BASIC CONTRACT
  • 暂停、过期、冷却或不在工作窗口的事件不会进入隐藏重试队列。
  • 接受时员工忙碌的事件保留跳过记录，不把它伪装成成功处理。
  • Core 离线期间的新事件不会在重启后补放；持续运行与任务状态要明确。
A输入 · 先把任务写清楚INPUT SPEC

任务示例：行业频道出现一篇新文章，分析员工提取要点并写下问题。任务平时等待事件；冷却、时段与当前状态共同决定本次是否执行，实际结果留在 Plan 中。

字段 / 对象本次示例它解决什么
原生事件channel.posted来自指定频道的首次成功新帖
显式事件signal + eventId通过授权触发入口发出信号
冷却按需要配置秒数控制相邻事件过密触发
等待nextAt 为空等真实事件，不表示已完成
结果运行 / 忽略 / 跳过按真实状态记录处理情况
示例字段对应真实目标、材料与处理范围。
B输出 · 文件与交接路径OUTPUT SPEC
输出文件内容与检查线索
event-brief.md来源、响应目标与触发条件
analysis.md本次新增内容的重点与出处
questions.md需要继续核对或讨论的问题
交接关系传递材料下一步动作
来源 → Core新帖首次成功发布产生与来源相连的事件
事件 → Plan来源与事件标识检查任务、条件与当前资格
Plan → 员工新增内容与处理指令执行一次明确的响应工作
员工 → 产物重点、出处与问题检查实际处理结果
记录 → 调整执行或未执行的依据继续修改冷却与工作范围
产物与传递关系分别保留，便于下一位继续。
